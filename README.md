# Интелигентна система за подпомагане управлението на софтуерни изисквания чрез Prolog

Практическа реализация. Системата представя софтуерни
изисквания като Prolog факти/правила, автоматично открива противоречия и
проблеми, формализира правила за тяхното откриване и
генерира препоръки за корекция през текстов потребителски
интерфейс.

## Технологии

- **SWI-Prolog** (тествано с версия 10.0.2), библиотека `plunit` за
  автоматизирано тестване.

## Структура на проекта

```
main.pl                    - входна точка на интерактивния интерфейс
src/
  kb_schema.pl              - схема на базата от знания
  requirements_data.pl      - примерен набор от 14 изисквания 
  conflict_rules.pl         - правила за откриване на проблеми 
  recommendations.pl        - модул за генериране на препоръки 
  interface.pl               - текстов потребителски интерфейс 
  evaluation.pl              - оценка спрямо ground truth + сравнение с
                                базов подход 
data/
  ground_truth.pl           - ръчно анотирани очаквани проблеми
tests/
  test_requirements.pl       - 29 unit-теста (plunit)
  run_tests.pl                - runner за тестовете
  evaluate.pl                  - runner за оценката/сравнението
```

## Стартиране

Интерактивен интерфейс:

```
swipl main.pl
```

Автоматизиран тестов набор:

```
swipl tests/run_tests.pl
```

Оценка на резултатите и сравнение с базов подход :

```
swipl tests/evaluate.pl
```

## Представяне на знанията 

- `requirement(Id, Type, Text, Priority, Status, Module)` - основен факт за
  изискване.
- `action(Id, Subject, Verb, Object, Modality)` - деонтично (must/must_not/
  should/should_not/may) триплетно представяне на действие в изискване, за
  логическо съпоставяне между изисквания.
- `attribute(Id, Name, Operator, Value, Unit)` - количествено (нефункционално)
  ограничение, напр. `attribute(req5, response_time, lte, 2, seconds)`.
- `depends_on(Id1, Id2)`, `excludes(Id1, Id2)` - зависимости между изисквания.

## Откривани проблеми 

| Тип проблема         | Описание                                                        |
|-----------------------|------------------------------------------------------------------|
| `action_conflict`     | Две изисквания задават несъвместими модалности за едно действие |
| `numeric_conflict`    | Несъвместими количествени прагове за един и същ измерим атрибут |
| `soft_inconsistency`  | Различни прагове за един атрибут - вероятно дублиране            |
| `ambiguous`           | Нееднозначен/неизмерим термин в текста                          |
| `incomplete`          | Липсва формализирано действие или количествен критерий          |
| `dependency_cycle`    | Циклична зависимост между изисквания                            |

## Резултати от оценката 

Спрямо ръчно анотирания тестов набор (15 очаквани проблема):

| Подход                                   | Precision | Recall | F1   |
|--------------------------------------------|-----------|--------|------|
| Prolog система (логически извод)          | 1.00      | 1.00   | 1.00 |
| Базово претърсване по ключови думи         | 1.00      | 0.13   | 0.24 |

Базовият подход, който само търси нееднозначни термини в отделни изречения,
структурно не е в състояние да открие противоречия, числови несъвместимости
или циклични зависимости, тъй като те изискват съпоставяне на структурирани
данни (действия/атрибути) между различни изисквания - нещо, което наивното
текстово търсене по дефиниция не прави. Това демонстрира добавената стойност
на логическия (Prolog-базиран) подход спрямо чисто лексикален анализ.
